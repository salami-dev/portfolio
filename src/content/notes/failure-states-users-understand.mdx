Failure states are product behavior. A timeout, rejected write, stale cache, or partial outage still needs design, copy, hierarchy, and recovery logic.

## A failure state is a contract

Useful failure states answer four questions:

- what happened;
- whether the user action was applied;
- whether retry is safe;
- what the user can do next.

```ts
type SaveState =
  | { status: "idle" }
  | { status: "saving" }
  | { status: "saved"; savedAt: Date }
  | { status: "failed"; retrySafe: boolean; message: string };
```

## Recovery table

| Failure | User-facing question | Interface requirement |
| --- | --- | --- |
| Timeout | Did my action work? | Show state uncertainty and safe retry guidance |
| Validation error | What must change? | Associate specific errors with fields |
| Partial outage | Can I continue? | Preserve completed work and disclose unavailable functions |

## Writing style

The useful version is specific and calm. It avoids blaming the user and avoids pretending that the system knows more than it does.
